# nanoPlayer iOS、安卓与 Pad 可行性分析

日期：2026-09-11
依据：当前桌面源码 v0.1.7 / main，以及文末官方资料。
范围：只分析可行性、技术路线、UI 复用边界和工作量；不制定排期、里程碑、任务清单，不开发移动端。手机 UI 重新设计，Pad UI 沿用现有桌面版本的布局与视觉基线。

## 1. 判断

**iOS/iPadOS、Android 手机/平板均可行，但不是桌面应用直接重新打包。** 已有资料库、歌词、评分和歌单成果有较高复用价值；决定投入的主要因素是系统文件授权、后台播放生命周期、格式兼容与真机质量，而不是多写几个响应式断点。

综合当前代码和“Pad 沿用桌面 UI”的约束，较合适的路线是 **Tauri 2 + React 共享界面组件与业务模型，iOS 用 Swift、Android 用 Kotlin 接入原生媒体和文件能力**。手机重做信息架构及交互，Pad 保留侧栏、中央资料库和底部播放器。这个推荐是工程判断，尚无本项目移动编译或真机实验支持。

Android 更接近现有“扫描本地音乐库”的产品语义；iOS 也支持用户选择文件或目录，但不能假设可以像桌面一样扫描任意路径、持续监听全部变化。两者后台播放都需要专门适配。Pad 减少的是界面重设计量，不会省掉平台底层工作。

## 2. 当前代码可以复用什么

| 当前成果与证据 | 移动端复用判断 | 实质变化 |
| --- | --- | --- |
| React 19、TypeScript、Zustand；`src/domain.ts`、`src/store.ts` | 类型、检索/筛选规则、歌词与部分状态逻辑可复用 | 手机页面重设计；播放事实状态不能继续仅由前端持有 |
| Rust SQLite/FTS5、5 个迁移、歌单/评分/覆盖；`src-tauri/src/database` | 数据关系与大部分 SQL 可复用 | 文件身份从绝对路径扩展为授权资源标识，迁移和恢复需适配 |
| `metadata`、`lyrics`、LRC 解析、LRCLIB | 规范化和匹配算法可复用 | 元数据读取入口改为可寻址流/句柄或受控本地副本；授权生命周期另处理 |
| `scanner`、`notify`、canonicalize、路径指纹 | 扫描规则可参考，桌面文件接口不能原样复用 | 文件提供者枚举、授权失效、资源重新关联、前台增量校验 |
| rodio/cpal/Symphonia 音频线程 | 解码能力可研究复用；不建议直接承诺照搬整个播放后端 | 系统音频会话、焦点、中断、输出路由、后台存活需要原生层 |
| `PlayerBar.tsx` 每 250ms 轮询并推进队列，`App.tsx` 每 5s 保存 | 是必须改变的边界 | WebView 暂停后，原生层仍须切歌、计次、保存并接收耳机/锁屏操作 |
| `navigator.mediaSession` | 浏览器层控制入口，不是移动原生后台会话证明 | 接入系统媒体控制并处理 UI 不存在时的命令 |
| `lib.rs` 有 `mobile_entry_point` | 仅入口注解 | updater、菜单、窗口、watcher 仍按桌面初始化；没有已验收的 iOS/Android 工程 |
| 安装器、GitHub updater、桌面 capabilities | 发布思路可参考，产物不可复用 | 移动签名、权限声明、商店分发、版本号和升级渠道独立适配 |

复用比例只能作设计层面的估计：业务模型/纯算法约 60%–80%，Pad 界面组件约 60%–80%，手机展示层约 20%–40%，系统适配约 0%–20%。这些是按模块职责估计的区间，未经逐行迁移统计，不能加权成“整项目复用率”或直接折算工期。

## 3. 文件和资料库的可行性

### iOS / iPadOS

系统文档选择器可以授予所选目录的 security-scoped URL；这不是全磁盘扫描授权。目录来自 Files 文件提供者时，还可能涉及云端占位文件、访问协调及资源离线。资源访问应由原生适配层管理授权、书签恢复与失效处理。[Apple 目录访问说明](https://developer.apple.com/documentation/uikit/providing-access-to-directories?changes=l_5&language=objc)

可选的产品语义有两种：

- **导入副本到应用容器**：播放路径、元数据读取和离线保证较直接；代价是重复占用空间、大批量导入时间，以及卸载后的数据恢复问题。复制不修改源文件，但需向用户明确空间成本。
- **原位置引用授权文件/目录**：更接近桌面资料库；代价是授权书签、外接盘断开、云提供者重新下载及文件移动后的恢复复杂度。保存一个路径字符串不足以保证下次可读。

若强调“离线稳定听歌”，受控导入副本更容易形成可预测行为；若必须管理外部目录，工作量和不确定性明显上升。两种均为分析选项，本轮不冻结选择。Apple Music 订阅曲目、DRM 内容及系统音乐库不等同于可读取的普通音频文件，不计入这里的本地文件兼容承诺。

### Android

SAF 的文件/目录选择和持久 URI 授权适合用户显式添加资料库；应用通过 `ContentResolver` 读取内容，不应把 `content://` 转成猜测的磁盘路径。持久授权不保证资源永不移动或被删除；Android 11 起部分根目录和 `Android/data`、`Android/obb` 等位置受到选择限制。[Android SAF 文档](https://developer.android.com/training/data-storage/shared/documents-files)

另一种入口是 MediaStore 音频集合，适合“发现设备已有歌曲”；它与 SAF 目录授权不是同一机制，权限和扫描模型不同。工程上可以选择其中一个主入口，不默认申请全文件访问。外置 SD 卡、厂商文件管理器和云提供者差异应计入质量成本。SAF 提供者未必给出可 seek 的文件描述符；解析和播放必要时需要应用缓存副本。

两平台都需要保留原来的只读原则：评分、歌单、封面、歌词写入应用存储；授权失效时标记不可用，重新授权后尽量保留 ID 和用户记录。桌面 SQLite 备份不能自动成为手机可用资料库，因为绝对路径和授权凭据不可跨设备直接复用。跨设备传歌、同步与账号不在本次基础工作量内。

## 4. 播放技术路线

### iOS / iPadOS

原生媒体层可采用 AVPlayer/AVQueuePlayer，配合 AVAudioSession 的 playback 类别与后台 audio 能力；锁屏元数据和远程控制由 MPNowPlayingInfoCenter / MPRemoteCommandCenter 接入。后台音频能力不意味着任意扫描、网络请求或 WebView JavaScript 都会持续运行。[Apple 媒体播放配置](https://developer.apple.com/documentation/avfoundation/configuring-your-app-for-media-playback?changes=la_4__5)、[后台执行模式](https://developer.apple.com/documentation/xcode/configuring-background-execution-modes)

原生层需持有队列、自然结束事件和恢复检查点；UI 重新激活后拉取真实状态。来电/其他音频中断、耳机拔出、蓝牙切换、音频路由变化和进程被系统结束后的恢复属于播放器本身的可靠性工作。退出恢复默认不自动播放，与桌面原则一致。

### Android

Media3 ExoPlayer + MediaSessionService 是对应的原生路径：播放器与媒体会话放在服务中，界面通过控制器连接；通知、锁屏和耳机控制不依赖页面挂载。服务需要声明媒体播放的前台服务类型和权限。[Media3 后台播放](https://developer.android.com/media/media3/session/background-playback?hl=en)

音频焦点和服务启动限制必须按目标系统版本处理。例如面向 Android 15 及以上时，音频焦点请求要求应用处于前台或运行前台服务；不同厂商的电池管理仍可能影响恢复体验。[Android 音频焦点](https://developer.android.com/media/optimize/audio-focus)

### 共享状态和格式边界

推荐由原生播放器持有播放事实状态，Rust 管理可复用规则/持久数据，React 发送动作并显示快照。自然结束计次采用会话 ID 去重，UI 恢复不重记次数。原生事件到 Rust 的调用必须在没有 WebView 回调参与时也可完成；这是 Tauri 桥接工作的一部分，不能假定现有 IPC 自动满足。

桌面列出的 MP3、AAC/M4A、FLAC、ALAC、WAV、Vorbis、Opus、AIFF 不能直接成为移动格式承诺。容器、编码、系统解码器、采样率及可寻址输入分别影响支持度；Android 官方也明确区分容器支持与样本解码支持。[Media3 格式说明](https://developer.android.com/media/media3/exoplayer/supported-formats)

如要求与桌面完整格式等价，可研究复用 Symphonia 解码并向原生音频输出送 PCM，但会增加 seek、无缝衔接、缓冲、耗电和故障诊断成本。AVQueuePlayer 或 ExoPlayer 的存在本身不证明所有格式无缝。输出设备应使用系统路由/选择器语义，不能照搬桌面“枚举并切换任意音频设备”的承诺。

## 5. 路线比较

| 路线 | 对当前项目的优势 | 主要代价 | 判断 |
| --- | --- | --- | --- |
| Tauri + React + Swift/Kotlin 原生媒体/文件层 | 保留 Pad 桌面界面与 Rust/TS 资产，桌面继续共用规则 | 原生插件、后台桥接、桌面 API 隔离仍需较多工程 | 与本次约束最匹配 |
| Tauri + 主要沿用 rodio/Rust 播放 | 解码逻辑更统一 | 平台生命周期仍需原生接入，格式以外的后台可靠性不会自动解决 | 技术上可探索，但成本不一定较低 |
| React Native + 原生媒体层 + 可选 Rust FFI | 复用部分 TS，手机原生交互基础较好 | DOM/CSS 组件不可直接复用；Pad 需重新实现桌面视觉，Rust FFI 多一层维护 | 手机体验优先、可接受 UI 重写时有价值 |
| SwiftUI/UIKit + Compose，分别原生 | 系统生命周期和媒体集成最直接 | 两套 UI 与平台实现，Pad 仅能复用设计，更多测试和维护 | 长期移动独立团队可考虑 |
| Flutter + 平台媒体插件 | 两个移动平台共用 UI | 现有 React UI/TS 业务迁移到 Dart，Rust 桥接与后台差异仍在 | 当前资产下无明显成本优势 |

Tauri 官方支持 Kotlin/Swift 移动插件，支持此混合架构方向；这仅说明框架能力，不证明仓库依赖全部支持移动目标。[Tauri 移动插件](https://v2.tauri.app/develop/plugins/develop-mobile/)

桌面 updater 应按平台隔离。Tauri 官方示例将 updater 依赖和初始化限定为桌面；移动版本走对应签名和分发渠道，不沿用当前 GitHub EXE/AppImage/app archive 更新流程。[Tauri updater](https://v2.tauri.app/plugin/updater/)

## 6. 手机重设计与 Pad 复用边界

手机应保留品牌、深浅主题、封面和歌词组件的视觉语言，重新组织为少量底部主导航、单列歌曲/专辑浏览、常驻迷你播放器和全屏正在播放。评分、文件夹过滤、批量选择和队列编辑需要触控入口；桌面的 hover、右键菜单、双击播放及密集多列表格不能作为唯一操作方式。长按/更多菜单、明确播放按钮和可返回的详情层级更适合手机。这里描述交互方向，不产出具体页面设计稿。

Pad 沿用侧栏 + 主内容 + 底部播放器 + 可选歌词/队列抽屉，保留桌面首页与专辑/艺术家信息组织。不重新设计一套平板产品，但需要安全区、触控点击面积、软键盘、横竖屏、分屏和可变窗口适配。窄分屏可收起侧栏/抽屉，不能机械套用桌面最小 720px；没有鼠标时仍须可排序、可编辑、可查看详情。macOS 红黄绿窗口控件和 64px 避让区不应原样出现在 Pad。

iPadOS 与 Android 平板分别共享各自手机的底层媒体服务，界面复用并不让它们成为桌面程序。平板独有成本主要来自布局和输入方式测试，而非重写资料库。

## 7. 工作量估计（人日，不是实施计划）

以下为熟悉 React/Rust 且具备 Swift/Kotlin 经验的团队累计有效工作量，1 人日按约 8 小时；包含设计、实现、集成和一般返工。估计置信度中低，未做移动样机、编译或性能测试。多平台人日不可简单当成自然日或按人数线性相除。

基础范围：本地无 DRM 文件、资料库搜索、歌单/评分、封面/歌词、可靠后台播放/锁屏控制、状态恢复、手机重设计与 Pad 桌面布局适配；不含账号/同步、NAS、CarPlay/Android Auto、DRM、完整音频发烧功能或所有国产商店接入。

| 成本组成（互不重复） | 人日区间 | 包含内容 |
| --- | ---: | --- |
| 共享模型、持久状态与平台接口调整 | 8–14 | 桌面逻辑隔离、资源标识、后台状态一致性 |
| 手机交互设计与共享 React 界面实现 | 15–24 | 信息架构、播放/资料库/歌单/歌词/设置的触控交互 |
| iOS 原生文件、音频和生命周期 | 18–30 | 导入/授权、音频会话、后台队列、锁屏、中断恢复 |
| Android 原生文件、音频和生命周期 | 15–25 | SAF、媒体服务、焦点、通知与资源失效 |
| Pad 复用与适配（两平台合计） | 6–10 | 分屏/旋转/输入/安全区，沿用桌面布局 |
| 双平台集成、真机质量与发布工程 | 15–25 | 基本设备矩阵、只读验证、迁移、耗电抽测、签名打包 |
| **双平台手机 + Pad 基础合计** | **77–128** | 不含下面的额外复杂场景 |

保留约 20%–30% 不确定性后，双平台四类设备较稳妥的投入区间约 **95–165 人日**。若只做一个平台，iOS+iPad 约 **55–90 人日**，Android 手机+平板约 **50–85 人日**（未加同等风险余量）；它们都包含共享层和手机重设计，不能相加来推导双平台总量。

增量敏感因素：严格实现桌面全部格式且补软件解码/高质量衔接，可能额外 15–30 人日；iOS 外部文件提供者和原位置大库管理深度可靠性，可能额外 8–15 人日；超出基础矩阵的 Android 厂商/外置盘兼容，可能额外 5–10 人日。这些粗估与风险余量可能重叠，不能机械全部相加。应用商店等待、账号/证书审批和硬件采购时间不属于有效人日。

维持四类设备的长期成本也会增加：系统升级、权限策略、后台服务、格式和分屏回归需要持续投入。当前尚无设备范围和使用量，无法给可信的年度维护报价。

## 8. 结论的边界

该分析足以判断“值得保留现有技术资产，并增加原生移动层”，不足以承诺已有移动兼容或确定交付日期。最大未定项是 iOS 文件使用语义、格式等价要求和目标设备范围。更窄的导入型离线播放器明显比“完整镜像桌面外部目录管理能力”的投入可控。

本轮只更新桌面文档与生成分析，未初始化移动工程、修改程序、安装移动 SDK、创建排期或发布移动包。
