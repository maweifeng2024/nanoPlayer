# iOS 资源库设计：0.1.23 基线

> 2026-10-16 使用反馈后的新交互、一级目录勾选和浏览器目录管理方案见 [资源库重新设计](LIBRARY_REDESIGN.md)。本文记录 0.1.23 基线；与新需求冲突的子项索引、固定 Wi-Fi 目标不再作为后续开发目标。新方案已接入 0.1.24 源码，SDK 更新后的最终构建与设备验收证据见状态文档。

2026-10-14 完成调研，用户随后确认采用本方案并要求完成实现。2026-10-15 已接入三类来源、文件夹管理、目标选择及复制/移动；实现证据与原生设备验收边界见 [STATUS.md](STATUS.md)。以下保留设计合同，不能把实现能力当作所有 Files provider 已验收。

## 推荐结构

沿用 Android 视觉语言，在现有“资料库 → 本地资料库”内改成“资源库”来源管理页；歌曲、专辑、艺术家仍是索引后的音乐浏览视图。资源库负责文件位置，歌单负责播放组织，两者分开。

推荐 **同一页三分区的文件夹列表**，全部来源一眼可见。每行显示名称、来源路径、歌曲数、状态和更多菜单；来源的“加入音乐库”开关沿用现有集合过滤语义，不能与文件多选混用。

```text
资源库                                    添加 ＋
搜索文件夹                         Wi-Fi 传歌

nanoPlayer                         可管理
  收件箱               12 首       ›  ···
  我的收藏             86 首       ›  ···
  演唱会               24 首       ›  ···

Files                              只读
  Files · iCloud Drive · 无损      ›  ···
  来源：iCloud Drive / Music / 无损
  248 首 · 已索引 · 加入音乐库 ☑

其他音乐 App                       只读
  foobar2000 · Music               ›  ···
  来源：在我的 iPhone / foobar2000 / Music
  96 首 · 已索引 · 加入音乐库 ☑

固定 mini player
首页                 资料库               歌单
```

iPhone 进入文件夹后采用单列列表、面包屑/返回和“选择”；多选时底部出现批量操作条，位置在播放器上方。iPad 宽窗口显示文件夹树与内容两列；600–900px 保留 72px 主导航侧栏、单列资源内容；更窄窗口保留 iPad 导航覆盖层。长名称两行显示并可在详情查看全名；图标、只读文字与状态共同表达含义，不只用颜色。普通触控目标至少 44pt。

备选方案是三标签页（nanoPlayer / Files / 其他 App）。优点是列表更短，缺点是新增来源和失效状态需要切页查看。推荐三分区，来源很多时支持折叠和搜索。

## 三类资源与权限

| 类型 | 文件位置 | 可操作 | 不提供的操作 |
| --- | --- | --- | --- |
| nanoPlayer | 应用 `Documents/Music/` 内的管理区；建议在 Files 中公开 | 新建/重命名文件夹、移动自有文件及文件夹、复制导入、Wi-Fi 接收、播放、索引 | 修改音频标签或音频字节；把评分/歌词写回源音频 |
| Files | 用户通过系统选择器授权的文件夹，例如 iCloud Drive、在我的 iPhone、第三方 provider | 只读浏览、选择加入索引、重新扫描、重新授权、复制到 nanoPlayer、移除索引 | 原地新建、重命名、移动、删除、覆盖 |
| 其他音乐 App | 该 App 在 Files 公开且用户选择授权的文件夹 | 同 Files；用音乐 App 名称区分来源 | 读取私有沙箱、订阅缓存/DRM、自动枚举所有音乐 App |

三类是产品展示分类，不是三个互不相交的系统存储空间。nanoPlayer 自己的 Files 公开目录归入第一类，不能重复作为外部来源添加。第三类本质上也是系统文件授权；不能承诺通过目录路径自动可靠识别 App。添加时预选 Files，用户可选择“其他音乐 App”并确认 App 显示名；系统能提供可靠信息时再预填。

外部只读由 native 层白名单执行，不能只隐藏按钮。允许编辑“来源显示名称/分类”等 nanoPlayer 记录，但不得改源文件夹名。移除来源只移除索引与授权，不删除源文件；涉及当前播放和队列时显示影响并按既有筛选规则更新。

## 导入、打开与 Wi-Fi

1. “添加”菜单：新建 nanoPlayer 文件夹、导入文件/文件夹到 nanoPlayer、添加 Files 文件夹、添加其他音乐 App 文件夹、Wi-Fi 传歌。
2. 外部来源：系统选择文件夹 → 确认来源分类/名称、只读说明和扫描子目录 → 添加并扫描 → 完成后加入音乐库。文件夹内容页支持选择部分文件/子文件夹加入索引；默认整个来源递归索引，选择规则持久化。重新添加同一来源打开已有记录，重叠父子来源提示复用，不静默制造重复歌曲。
3. “用 nanoPlayer 打开”：先进入“保存到 nanoPlayer”页，预选 `收件箱`，可选择已有文件夹或新建；确认后复制、校验、入库并可播放。不自动把一次性授权当长期引用。若未来需要“不保存只播放”，应作为另一个明确选项，不混入本轮默认流程。
4. 常规导入同样选择目标；从自有文件夹发起时预选当前文件夹。源层级默认保留，可预览实际目标路径。
5. Wi-Fi 页面先选择 nanoPlayer 目标文件夹，再开启接收；显示目标、地址/二维码、配对码、上传进度和结果。服务运行时锁定该会话目标；切换目标须先停止。地址二维码不包含配对码，八位码每次启动更换，单文件上限 512MB。保留前台接收/关闭即停的既有合同；后台续传不在本轮承诺内。
6. 上传和导入先写管理区临时文件，完成、格式/大小检查及字节校验后原子落位并索引；失败不留下半首歌，旧文件不被覆盖。批量显示逐项成功/失败，可重试失败项。

## 移动与文件夹编辑

“编辑文件夹”本轮指新建、重命名和移动层级；删除空文件夹可提供，非空文件夹/音频的物理删除不默认加入本轮，若需要须单独确认产品行为。

自有内容页：选择文件/文件夹 → “移动到” → 选择 nanoPlayer 内目标 → 显示目标与同名处理 → 确认移动。目标选择器支持“新建文件夹”，禁止移入自身或后代、移到当前位置以及任意外部目标。根目录 `Music` 不可重命名/移动。

只读内容页对应操作为“复制到 nanoPlayer”，不出现“移动”。批量选择必须限于同一来源，不混合自有移动和外部复制。

操作不改音频字节；移动保持 track ID、评分、统计、歌单和队列引用，路径在 native 文件操作成功后事务更新。重命名父文件夹须同步所有后代路径。当前播放涉及的文件建议暂缓移动，暂停后完成重定位/恢复进度；以 AVPlayer 真机验证为准。中断、空间不足、权限变化必须有逐项结果与恢复日志，不能宣称跨文件和数据库操作天然原子。

现行仓库“音乐目录只读”规则继续适用于所有外部原始音乐。实现自有管理区移动前需把已确认的新能力、目录白名单及字节不变测试一起写入当前架构/安全规则，不能扩展为任意路径写入。

## 名称与重复规则

名称用于阅读，内部 UUID 用于身份；不能用显示名称、绝对沙箱路径或短哈希作为唯一身份。

| 情况 | 推荐显示名 |
| --- | --- |
| 自有文件夹 | 原文件夹名，如 `演唱会` |
| Files 已知位置 | `Files · iCloud Drive · 无损` |
| Files 位置未知 | `Files · 无损`，详情显示系统可提供的来源信息 |
| 其他 App | `foobar2000 · Music`；若只选择 App 根则 `foobar2000` |
| 上述组合仍重名 | 第二个起追加 `（2）`、`（3）`，持久保存、删除不重排 |

显示名候选先 trim、Unicode NFC 和大小写折叠做冲突判断；保留原名用于展示。后缀本身与已有名字冲突时继续选择可用名称。用户编辑显示名也经过同一全库唯一性校验。身份使用持久 `sourceId`，bookmark 续期或重新授权保持 ID；bookmark 二进制不等同稳定身份。解析后的授权根 URL/可用 resource identifier 用于同一目录去重，无法确认身份时明确询问已有来源重新连接。

自有同级文件夹禁止空名、`.`/`..`、分隔符及非法名称，按目标文件系统等价规则检测冲突；相同名称建议 `演唱会（2）`。导入/移动文件撞名默认“保留两份”，扩展名前加后缀，如 `Track（2）.flac`，提供跳过；本轮不提供覆盖。文件夹撞名默认新目录后缀，不自动合并。并发上传通过原子占位确认最终唯一名。

重复导入同一目标且字节完全相同可提示跳过；同标题不同文件不自动合并。同一原始文件的外部引用和自有副本属于不同位置，保留来源信息，不自动搬移评级到另一份。

## 状态与验收

外部来源显示：扫描中、可用、需下载、需重新授权、来源不可用、扫描失败；`stale bookmark` 优先尝试续期，失败才要求重选。云端文件未下载时允许显式下载/重试，不把云端占位符报告成损坏音乐；授权失效保留评级/歌单/来源记录。显示歌曲数、最后扫描时间及失败入口，成功导入后状态切到可用。

后续实现验收：Files 与两个实际公开目录的音乐 App；本地/iCloud、云端未下载、撤销权限、源改名/移动、重复父子来源；新建/改名/移动/批量冲突/中断恢复；文件前后 SHA-256 一致；移动后 ID/评分/统计/歌单/队列/重启一致；Wi-Fi 多文件/Unicode/同名/大文件/空间不足。覆盖 iPhone/iPad 横竖屏、窄窗口、VoiceOver 和大字体。只有浏览器预览不能证明 native 文件能力。

## 实现与验收边界

共享桌面/Android 仍使用原有 `LibraryPage`，iOS 使用独立资源库边界。Swift `NativeLibrary` 管理带 schema version 的来源记录、目录白名单、冲突规则、字节校验和移动日志；旧 bookmarks 迁移为 Files 来源，旧管理区音频保留原位置与文件名。Rust 事务同步路径并保留 root/media/track ID；扫描按来源的相对路径范围过滤。

导入与 Wi-Fi 可选目标；Wi-Fi 同名追加序号而非 UUID 前缀。系统“用 nanoPlayer 打开”先暂存到应用支持区，再显示目标保存页，保存完成才进入管理区与音乐索引。音频内容无标签写回。云端占位文件显示需下载提示，由用户在 Files 下载后重试；没有承诺所有第三方 provider 自动下载或后台读取成功。外部物理删除、写入及后台 Wi-Fi 接收不在范围内。

Files/iCloud/其他 App 的实际授权、系统打开方式、真实 Wi-Fi 上传、移动中断后真实设备恢复和后台播放仍按状态文档逐项验收；浏览器演示不会操作设备文件。

## 调研依据（2026-10-14）

- [Apple：Providing access to directories](https://developer.apple.com/documentation/uikit/providing-access-to-directories)：通过系统选择器取得目录授权，使用 security-scoped URL；目录访问不等于可枚举其他 App 私有目录。
- [Apple：UIDocumentPickerViewController](https://developer.apple.com/documentation/uikit/uidocumentpickerviewcontroller)：外部文档/目录访问与授权生命周期。
- [Apple：Files 的文件及文件夹整理](https://support.apple.com/en-mide/guide/iphone/iphab82e0798/27/ios/27)：新建、重命名、复制和移动的系统交互；App 名称标记的目录存在操作限制。参考其层级和操作词汇，不继承外部写权限。
- [Apple HIG：File management](https://developer.apple.com/design/human-interface-guidelines/file-management)：文件管理规范入口；当前抓取只有 JavaScript 页面，未把无法取得的正文当作具体规范证据。
- [Evermusic / Flacbox：Local Files](https://everappz.com/docs/guide/evermusic/evermusic-guide-local-files/)：官方指南将应用内文件与设备/其他应用文件分开，提供选择、新建、复制/移动和传输队列。nanoPlayer 借鉴位置与音乐库分离；外部只读是本产品要求，区别于其可写连接。
- [foobar2000：iOS changelog](https://www.foobar2000.org/changelog-ios)：官方记录涉及音乐文件夹在 Files 的可见性修复。说明公开目录可见性需要实测，不能推断每个 App 都开放同样能力。

推荐方案是上述规范、产品资料与用户要求结合后的设计判断，不是 Apple 强制指定的三分区结构。

## 用户已确认的决定

1. 布局：同页三分区（推荐）或三标签页。
2. 外部来源命名：`Files · 位置 · 文件夹` / `App · 文件夹`，冲突加稳定序号；允许编辑显示名。
3. 保存/移动：打开时选择自有目标，默认收件箱；Wi-Fi 会话固定目标；自有移动、外部只复制；同名保留两份/跳过。

用户已确认采用推荐的三项方案。自有音频物理删除、外部写入、后台 Wi-Fi 接收均未包含；仅允许删除空的自有文件夹。
