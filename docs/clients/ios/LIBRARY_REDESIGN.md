# iOS 资源库重新设计

2026-10-16。针对 0.1.23 使用反馈的已确认方案；0.1.24 已接入源码，SDK 更新后已恢复 iOS 构建与模拟器验证，真机验收独立记录，不能把本文视为验收结论。用户本轮五项要求优先于旧设计：只读引用、明确复制、浏览器管理自有目录、只勾选一级目录。本文覆盖旧设计的交互、索引范围与固定 Wi-Fi 目标规则；已实现状态仍以 [STATUS.md](STATUS.md) 为准。

## 1. 统一概念与首页

“资源库”只管理来源、位置及是否参与歌曲浏览；“歌曲/专辑/艺术家”展示索引结果；歌单组织播放。界面不再要求用户理解“索引全部”“仅索引选中项”。

首页同页两区：nanoPlayer（可管理）和外部来源（只读）。第三方公开文件夹与 Files 使用同一种文件授权，只在来源副标题标记 App，不再让用户先填写一个 App 名称假装完成接入。Apple Music 是独立的服务来源，不能伪装为文件夹。

```text
资源库                              添加 ＋

nanoPlayer                         Wi-Fi 传输
☑ 收件箱              12 首             › ⋯
☑ 我的音乐            86 首             › ⋯

外部来源                           只读
☑ 无损                248 首            › ⋯
  Files · iCloud Drive
☑ Music               96 首             › ⋯
  foobar2000 · 公开文件夹

勾选的一级目录及其所有子目录参与音乐库
```

首页只显示可勾选的一级记录；点名称进入浏览，点勾选只改变参与范围，点更多只打开菜单。iPhone 使用单列、返回与面包屑；宽 iPad 可显示来源/内容两列，窄 iPad 继承现有导航边界。进入目录后不再出现任何子项勾选框；播放、返回、重新扫描与更多操作使用明确按钮，触控目标至少 44pt。搜索来源与当前目录搜索分别命名，避免搜索含义随页面隐式改变。

正式界面不包含审核原型的“查看参与音乐库的歌曲”按钮；歌曲、专辑、艺术家等既有页面直接同步筛选结果。

“添加”仅列：引用 Files 文件夹（只读）、复制文件到 nanoPlayer、新建 nanoPlayer 文件夹；Apple Music 仅在真实适配可用后提供“连接 Apple Music”，不展示假连接成功。添加文件夹先系统选取，再确认名称与来源说明，不先填一大张表。

## 2. 一级目录的精确定义

- 自有区：`Documents/Music` 的直接子目录，每个目录一条记录，递归包含后代。根目录音频不自动搬移，展示虚拟一级记录“根目录音乐”，只包含根层音频。根容器本身不再提供总开关，避免父子勾选冲突。
- 外部区：每次授权的根文件夹是一条一级来源记录，无论其在 Files 原始层级多深；内部所有后代继承此记录。Apple Music 若接入则整个服务是一条一级记录。
- 只允许首页一级记录勾选，深入子目录、单首歌曲、批量操作都不提供勾选；文件管理改成单项更多菜单的移动、重命名、复制。目标选择器可以进入任意深度，使用“保存到此文件夹”，不使用勾选框。
- 新添加来源默认参与音乐库；取消只隐藏其音乐，不撤权、不删音频、不清空评分/歌单/统计。全取消明确显示空状态。混合歌单保留、排除歌曲置灰且跳过；播放队列同步，当前歌仍有效时保留进度，否则按现有移除当前歌曲规则处理。

一级目录使用持久 UUID；选择状态独立于绝对路径、名称和扫描 root ID。改名、移动或沙箱路径变化不丢选择。自有子目录跨一级目录移动后按新归属决定是否可播放；track ID、评分、统计与歌单保持。不为每个子目录创建重复扫描 root；扫描、查询和原生队列共享同一参与规则，避免 UI 筛掉但原生仍播放。

## 3. 引用与复制必须分开

| 动作 | 授权与结果 | 音频落地 |
| --- | --- | --- |
| 引用 Files 文件夹 | 取得 security-scoped bookmark，保存来源并只读扫描 | 不向 nanoPlayer Music 创建副本 |
| 复制文件到 nanoPlayer | 明示“将创建副本并占用空间”，先选目标再确认 | 仅写目标管理区，原件保持不变 |
| 外部条目的“复制到 nanoPlayer” | 显示原位置、目标与冲突策略 | 创建独立副本，不改原来源归属 |
| 在 Files “用 nanoPlayer 打开” | 单次打开授权不能冒充长期来源；显示明确的保存确认，可取消 | 兼容当前临时暂存，但确认前不进入 Music 或歌曲索引；取消清理暂存 |

引用后歌曲出现在“全部歌曲”属于正常只读索引；只有在 nanoPlayer 自有目录实际出现副本才是复制。详情必须同时显示“原始位置”“访问方式：只读引用”和“存储于外部”，避免把可播放误解成已经导入。

代码核查：`pickIOSSource` 显式传 `mode: reference`；Swift 对该模式注册来源和保存授权，不调用 `NativeLibrary.copy`。`importIOSFiles` 传 `mode: copy`，Swift 缺省模式也是 copy；系统打开则先暂存并等待保存。当前证据不足以确定用户测试走了哪条路径，不把“引用自动复制”报告为已经复现。开发时给模式使用封闭枚举并拒绝音乐选择请求缺省模式，记录脱敏操作类型、sourceId 与目标类型，避免遗漏参数静默变成复制。

权限失效保留记录与音乐元数据，提供重新授权；云端未下载提示去 Files 下载后重试，不能默默复制到自有库绕过。相同目录重复添加复用记录，父子重叠来源拒绝并指向已有记录。授权失败不得留下“成功”来源；取消不得改变歌曲数或磁盘内容。

旧版已复制音乐不自动删除、不自动认定原始来源、不反向迁移；用户可以逐个检查位置后自行处理。没有可靠身份信息时，不按同名猜测来源。

## 4. Apple Music 与网易云音乐

| 来源 | 能做的设计 | 约束与本轮定位 |
| --- | --- | --- |
| Apple 系统音乐库 | 用户明确授权后，独立“Apple Music”记录展示可取得的库内容 | 用 MediaPlayer/MusicKit 官方接口；库记录不等于可导出的音频文件 |
| Apple Music 订阅内容 | 可研究 MusicKit 浏览与官方播放器播放 | 不复制订阅缓存；需单独播放器适配及账户/订阅/地区/离线能力验证 |
| 网易云及其他音乐 App | 对实际公开在 Files 的文件夹只读引用；用户明确导出的普通音频可引用其目录或复制 | 本次未找到可用于读取该 App 私有本地库的官方接口证据，不能承诺直接接入或读取下载缓存 |

“已安装”不等于“已授权”或“可读取”。不自动枚举已安装音乐 App，不因用户输入“网易云”就创建有歌曲的可用记录。选取成功后才创建真实文件来源；没公开文件夹时显示“不支持从此 App 直接读取，请使用其导出功能（若提供）”。

推荐把 Apple Music 正式接入列为独立阶段：数据模型先区分 `file` 与 `service`，服务记录以 provider+itemId 标识，不能交给 Rust 文件路径扫描器或当前 AVPlayer 文件队列。适配验证必须覆盖切换播放器不双响、后台/锁屏、seek/跳过/错误、队列恢复、统计与退出授权。未完成这些门禁前不把服务曲目混入本地播放队列，也不把无法播放的列表冒充可用资源库。只有连接与读取权限，不调用修改 Apple 资料库的接口。

依据：[MPMediaLibrary](https://developer.apple.com/documentation/mediaplayer/mpmedialibrary)、[MusicKit](https://developer.apple.com/documentation/musickit)、[MusicAuthorization](https://developer.apple.com/documentation/musickit/musicauthorization/request())、[assetURL](https://developer.apple.com/documentation/mediaplayer/mpmediaitem/asseturl)、[受保护媒体标识](https://developer.apple.com/documentation/mediaplayer/mpmediaitem/hasprotectedasset)。这是能力边界调研，尚未对用户设备的 Apple Music/网易云做原生验证。

## 5. Wi-Fi 从上传页变成自有资源库管理页

手机进入“Wi-Fi 传输”并主动开启，显示地址、二维码、配对码与连接状态。浏览器输入配对码后，展示整个 nanoPlayer Music 管理区，而非手机预先锁定的一个目标目录。外部 Files 与服务来源完全不暴露。手机保持前台，关闭/停止即失效；保留现有单文件 512MB 上限和同名默认保留两份。

浏览器：面包屑、目录列表、当前位置、新建文件夹、目录更多菜单（重命名、移动、删除）、“上传到此目录”、逐文件进度与重试。可浏览并选择任意深度目标；手机一级目录勾选限制不影响传输目的地。默认进入手机当前自有目录或收件箱，用户可回到根再选择。

“编辑目录”指重命名与移动，不编辑音频字节。空目录删除直接确认；非空目录删除显示子目录数、音频数及播放影响，确认后先移入应用私有回收站，提供恢复/彻底删除。回收站不在 Music 扫描范围内；恢复保留 ID 和用户数据，同名需选保留两份或其他目标。彻底删除再次确认；本轮不引入自动清空策略。Music 根与系统收件箱不可删除/改名/移动，普通目录不能移入自身或后代。

删除包含当前播放/上传目标/移动任务的目录时返回“正在使用”，先停止相关任务再操作，不允许一半成功。排队上传在任务创建时固定目标目录 ID，每项执行前重新校验；目标被移除则暂停该项并要求重选，不能悄悄回退到根目录。目录改名后按稳定 ID 继续，页面更新路径。

所有浏览、目录编辑、上传与回收站操作必须配对后才能调用；首页只返回静态登录壳。会话凭证不放二维码、URL或持久存储；配对限流，停止即销毁。相同来源校验和无跨域开放继续适用；未认证目录列表也应拒绝。页面使用文本转义展示文件名，禁止把名称拼为 HTML。局域网 HTTP 不加密需在开启页简短说明，不对公网开放、不后台常驻。

已接入的 API（原生设备验收待完成）：会话创建/注销，目录列表，创建目录，重命名/移动，删除到回收站/恢复/彻底删除，上传任务。只接受会话内不透明目录/条目 ID 和合法名称；服务端解析到管理区，拒绝 traversal、符号链接逃逸及外部 sourceId。复用 NativeLibrary 的路径检查、冲突处理与移动日志，不能另写一个只靠字符串拼路径的 HTTP 文件管理器。写操作经同一串行协调器，附目录 revision 校验，冲突返回刷新提示；上传流不占住整个协调器，仅在目标预留和完成落位时短暂串行化。

成功上传逐项完成原子落位后触发增量索引，手机不必等停止接收才看到新歌；删除/移动完成后同步 SQLite 路径、参与范围和原生队列。回收站使用可恢复操作日志协调文件与数据库；中断恢复不把不存在文件显示为可播放，不丢评分与歌单记录。

## 6. 实施顺序与升级

1. 先建立一级目录持久身份与参与状态、原生筛选和迁移，再接首页；移除子项勾选及子项索引操作。旧整来源全选/全取消完整继承；旧部分索引无法无损表示时标记“需确认一级目录范围”，在用户确认前保留原有效集合，不静默扩大或缩小。确认后一次切换并保留旧规则备份，失败回滚。
2. 拆开只读引用与复制入口，显式操作模式；补来源详情与失权恢复，复现用户 Files 路径问题。
3. 将目录修改收口到原生协调器，完善回收站/恢复日志；接浏览器认证、浏览、建目录、重命名/移动/删除、选目录上传与手机同步。
4. Apple Music 做独立技术验证后再决定正式接入；网易云以真实公开目录/用户导出证据决定支持，不能用手工分类代替集成。

对现有数据只做有版本、可恢复的迁移，不自动移动音乐，不合并同标题的外部引用与自有副本。本次实现准备共享版本 0.1.24，Android build 1024、iOS build 7；本地构建证据与原生验收边界见 [当前状态](STATUS.md)。桌面发布由用户执行。

## 7. 开发验收合同

- 交互：iPhone/iPad 深浅色、横竖屏/窄窗口/大字体；点击行、开关与更多各自独立，菜单第二次点击关闭、焦点恢复。子目录及文件无勾选框，目标选择仍可进入深层目录。
- 选择：自有两个一级目录和外部两个授权根，覆盖默认全选/部分/全取消/重启/新目录/改名/移动；所有歌曲集合、混合歌单、原生队列与恢复一致。
- Files：合成音频在引用前后检查源 SHA-256、Music 目录清单及字节数；播放、重扫、重启后仍无自有副本。复制只有明确确认才新增副本，源 SHA-256 不变。分别覆盖系统打开、引用和复制，取消/失权/云端未下载/重复来源。
- Wi-Fi：真实桌面及另一移动浏览器配对、浏览、新建多级目录、改名、移动、删除空/非空目录、恢复、选择深层目录上传；并发/重复请求、过期 revision、错误配对、停止、断网、切后台、空间不足、Unicode/HTML 名称、同名、超限、目标变化和路径攻击。上传前后合成文件 SHA-256 一致。
- 迁移：0.1.23 全选/部分索引/失权/根层音频、回收站与移动中断；track ID、评分、统计、歌单、队列恢复可证明保留。设备日志和截图记录具体版本；浏览器 mock 不替代 native 文件或 Wi-Fi 验收。
- 可执行开发完成后按 [回归清单](../../development/REGRESSION_CHECKLIST.md) 与 [发布流程](../../release/RELEASE_PROCESS.md) 执行适用门禁，生成本次本地非桌面产物；桌面发布继续交给用户。
