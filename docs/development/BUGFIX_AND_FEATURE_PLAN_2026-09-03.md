# nanoPlayer 缺陷修复与功能迭代计划

日期：2026-09-03  
状态：本轮开发已完成，自动化与 macOS 原生壳层验收已通过

## 1. 当前进度判断

项目已经具备第一版纵向闭环：Tauri 2 + React/TypeScript 前端、Rust/SQLite 资料库、rodio/cpal/Symphonia 播放、目录扫描、歌曲/专辑/艺术家页面、歌单、队列、歌词和设置。本轮已将 9 个问题和已确认的产品决策落地，并同步更新实现状态文档。

自动化现在覆盖真实后端播放状态接口、进度填充、抽屉响应式宽度、专辑/艺术家一次切换、播放最多过滤、应用内对话框、元数据覆盖和歌单闭环。macOS 调试应用已完成启动、迁移、停止态恢复、列表和详情弹窗验收。音频能耗、多设备与长时稳定性仍属发布资格验收，不在本次功能完成的自动化结论中。

## 3. 功能调整方案

### 3.1 歌曲详情与元数据

- 单击歌曲标题或非操作区域打开详情；播放图标仍单击播放，双击整行是否保留播放由产品确认。
- 详情首批字段：封面、标题、曲目艺术家、专辑艺术家、专辑、年份、流派、作曲者、碟号/总碟数、曲号/总曲数、时长、格式、比特率、采样率、声道、文件路径、歌词来源、MusicBrainz ID。
- 推荐采用“应用内元数据覆盖”：新增 `track_metadata_overrides`，保留扫描原值和用户覆盖值；重扫不丢覆盖，可逐字段恢复原值；音乐源文件继续保持只读。
- 若选择“写回音频标签”，需要另立安全里程碑：格式兼容矩阵、写前备份、临时文件 + 原子替换、权限丢失、失败回滚和源文件哈希验证。这会改变当前产品承诺，不与本轮普通 UI 修改混做。
- 歌曲表新增独立“艺术家”列，不再只放在标题副行；排序键增加艺术家。窄宽度下优先保留标题、艺术家、时长和操作，随后再显示专辑、评分、添加日期。

### 3.2 专辑与艺术家

- 专辑详情：固定小封面置于上部左侧；元信息位于封面右侧或窄屏下方；歌曲表从下一行开始，禁止与封面同一网格层叠。多碟仍可分组。
- 艺术家详情：上部固定小图 + 艺术家摘要；下部只显示一个扁平歌曲表，不再按专辑逐段展示，也不重复“热门曲目”。默认按专辑、碟号、曲号稳定排序，并允许用户改列排序。
- 当前没有可靠的独立艺术家图片来源。默认建议使用该艺术家的最多 4 张专辑封面拼图或文字占位，不新增自动联网抓图。

### 3.3 导航与歌单

- “流派”从一级导航和页面路由移除，但继续读取、索引并在歌曲详情中展示流派，避免数据能力倒退。
- 歌单支持新建、重命名、删除、自定义图片、自动封面、添加/移除/批量添加和拖动排序。
- 自动封面规则：按“艺术家 + 专辑”在歌单中的出现次数降序选取最多 4 张有效图片，同次数以歌单当前内容为种子随机打散；歌单增删歌曲后自动重建。1 张铺满、2 张二分、3–4 张四宫格；无图使用稳定色和歌单首字。
- 自定义图片复制到应用管理目录或数据库缓存，不引用易失效的外部绝对路径，也不写入音乐目录；支持恢复自动封面。
- 歌单页显式提供“添加歌曲”按钮和可搜索选择器；空歌单不再只提示去歌曲页找隐藏菜单。

### 3.4 播放栏歌词入口

- 将麦克风图标改为简洁的“词”字文本图标；保持 30×30 点击区域、`aria-label=歌词`、选中态、tooltip 和 `⌘L`。

## 4. 播放引擎与能耗预研结论

短期不建议直接替换 rodio/cpal。当前 rodio 0.22.2 已提供 `Player::get_pos()` 获取真实播放位置，Decoder Builder 支持格式提示、可靠 seek 和 gapless 配置；Symphonia覆盖现有主要格式并提供 SIMD 优化。先把现有引擎从“前端模拟状态”改成“后端真实状态”，通常比换引擎更低风险。

计划中的技术验证：

1. 建立基线：暂停、普通播放、无损播放、切歌、seek、扫描同时播放五个场景，记录 CPU、唤醒次数、内存、磁盘 I/O、音频 underrun 和整机能耗。
2. 状态同步：使用 `get_pos()` 和 ended/empty 状态，UI 更新频率控制在视觉足够的 4–10Hz；歌词只在活动行变化时滚动，暂停或抽屉关闭时停止无意义定时器。
3. 解码与队列：用 Decoder Builder 传入 byte length、扩展名 hint 和 gapless；提前准备下一首但限制预读；不在音频回调线程访问 SQLite、网络或扫描任务。
4. 输出质量：避免无必要的软件音量叠加、重复重采样和削波；记录输入/输出采样率、声道和设备配置。所谓“提高音质”以“无额外失真、无非必要重采样、无爆音/断流”为标准，不承诺把有损源变得更高保真。
5. 依赖收窄：核对 `symphonia-all` 和 `experimental` 是否确实需要；只在格式矩阵不退化时裁剪功能，比较包体、冷启动和 CPU 后再决定。
6. 只有在 Instruments/采样剖析证明跨平台栈是主要瓶颈时，才评估 macOS 专用 Core Audio/AVFoundation 后端；否则保留统一 Rust 核心，降低三平台分叉成本。

验收采用同一台机器、同一输出设备、同一组曲目做变更前后对照；使用 Instruments Time Profiler、Energy Log/File Activity 等工具。先测基线再冻结目标，不用未经测量的绝对 CPU 百分比作为承诺。

技术依据：

- [rodio Player 0.22.2](https://docs.rs/rodio/0.22.2/rodio/struct.Player.html)
- [rodio Decoder Builder 0.22.2](https://docs.rs/rodio/0.22.2/rodio/decoder/builder/struct.DecoderBuilder.html)
- [Symphonia 格式、gapless 与 SIMD 支持](https://docs.rs/symphonia/latest/symphonia/)
- [Apple 应用性能分析](https://developer.apple.com/documentation/xcode/improving-your-app-s-performance)
- [Tauri 窗口拖动区域](https://v2.tauri.app/zh-cn/learn/window-customization/)
- [LRCLIB API 与限流规则](https://lrclib.net/docs)

- 一次解决 B1、B2、B4，并补静音、设备、结束、错误和恢复测试。

- 解决 B3、B5、B6、B7；移除流派一级入口。

### M4 歌单完整闭环（4–6 人日，P1）

### M5 在线歌词可靠性（2–3 人日，P1）

- 用用户出错样本复现 B9；改造 provider 错误模型、精确匹配/搜索降级、节流与诊断。
- 验证断网、无结果、429、5xx、超时和响应字段变化；所有失败均不得中断播放。
- 已完成搜索字段编辑、标题版本标记和主艺术家规范化、四级查询、候选去重、置信度、匹配原因、时长差和歌词预览；不确定结果必须由用户选择后才写入应用缓存。
- 已修复 LRCLIB 同时返回 `name` 与 `trackName` 时整批候选解码失败的问题；单条异常数据现在只跳过该条。

### M6 性能与音质工程（3–5 人日 + 长时测试，P1）

- 先采集基线，再实现经剖析证明有效的优化。

## 7. 已确认的产品决策

以下决策于 2026-09-03 确认，后续开发与验收以此为准：

1. **元数据采用应用内覆盖**：只修改 nanoPlayer 内的显示、搜索和聚合结果，不写回 MP3、FLAC、M4A 等源音乐文件；必须保留扫描原值，并支持逐字段恢复原值。
2. **保留双击播放**：单击歌曲标题或行内非操作区域打开歌曲详情；双击歌曲行播放；行内播放按钮继续支持单击播放。
3. **流派只移除独立入口**：从一级导航和独立页面移除“流派”，但继续读取、索引、搜索并在歌曲详情中展示流派数据。
4. **自定义歌单图片复制到应用数据目录**：用户选择图片后复制到 nanoPlayer 管理的目录，不修改原图、不依赖原始图片路径，暂不增加在线搜图。
5. **艺术家图片采用本地封面组合**：最多使用 4 张去重后的专辑封面生成拼图；没有可用封面时使用稳定色与文字占位，暂不联网抓取真实艺人照片。

这五项决策不改变“音乐源文件只读”和“在线能力默认关闭”的产品原则。
